DZ 21:

    1). Связь покупателей с товарами:
        - поле Product.buyers — ManyToManyField к User;
        - промежуточная модель — Purchase;
        - related_name пользователя: purchased_products;
        - Purchase хранит обязательное поле price_paid и дату purchased_at.
    
        В проекте допускается повторная покупка одного товара одним пользователем, исходя из логики проекта.
        Каждая покупка является отдельной операцией и хранит собственные price_paid и purchased_at.
        Поэтому ограничение уникальности пары user — product намеренно не используется.
    
    2). Добавление связи через ManyToManyField:
        В Django shell проверен метод add() с промежуточной моделью.
        Вызов без through_defaults:
            product.buyers.add(user)
        завершается ошибкой:
            IntegrityError: NOT NULL constraint failed: main_purchase.price_paid
        При передаче обязательного поля:
            through_defaults={'price_paid': product.price}
        связь успешно создаётся.
        Повторный вызов add() для той же пары user — product не создаёт новую Purchase.
        Поэтому реальная операция покупки в проекте создаёт отдельную запись Purchase,
        что позволяет хранить историю повторных покупок.
    
    3). Покупки:
        - POST покупки: /product/<product_id>/buy/
        - страница "Мои покупки": /purchases/
        Гостю кнопка покупки не показывается.
        Прямой POST гостя перенаправляет на страницу входа с параметром next.
        GET-запрос на адрес покупки возвращает 405.
    
        На странице товара отображается история покупок текущего пользователя.
        Страница "Мои покупки" доступна только авторизованному пользователю,
        показывает покупки от новых к старым и общую потраченную сумму.
    
        Автору разрешено купить собственный товар после дополнительного подтверждения, опять же из логики проекта.
    
    4). Оптимизация запросов:
        В двух существующих списках товаров используется defer('description'):
        - страница новинок;
        - страница категории.
    
        Проверка через CaptureQueriesContext для пяти товаров:
        - обычная выборка и обращение к name — 1 запрос;
        - defer('description') без обращения к description — 1 запрос;
        - defer('description') с последующим обращением к description каждого из 5 товаров — 6 запросов.
    
        Таким образом, defer() не создаёт дополнительных запросов, пока отложенное поле не используется.
    
        Сравнение двух способов получения покупок пользователя:
        - user.purchases.all() — 1 запрос;
        - Purchase.objects.filter(user=user) — 1 запрос.
    
        На странице "Мои покупки" используется select_related('product') и only().
        Получение списка покупок вместе с используемыми данными товаров выполняется за 1 запрос
        независимо от количества покупок.
        Общая сумма покупок вычисляется отдельным агрегирующим запросом.
    
    5). Удаление связанных объектов:
        Проверено каскадное удаление Purchase при удалении Product.
        В transaction.atomic() после удаления товара связанная Purchase отсутствовала.
        Транзакция была отменена через rollback, поэтому тестовые данные сохранены.
